# @t4r71/dsh-plan-tree

[English](README.md) | 中文

## 概述

`dsh-plan-tree` 给 agent 一份人能看见的计划：一次调用声明完整的步骤树，之后每次调用只把单个节点移过 `pending`、`in_progress`、`completed` 或 `blocked`。树存在会话日志上并折叠成 `planTree` 投影，右侧边栏据此画出实时计划（含嵌套），而每次更新都只是一条很小的日志记录。当工作的结构本身值得被看见时挂载它；只有一步的任务不需要。

<a id="use-this-package"></a>
## 使用本包

挂载本包会加入两个工具与一个投影单元，不需要写任何配置。模型负责声明并推进计划；投影则是客户端读取后用于绘制的内容。

### 何时选择它

当一项工作有若干步骤、且用户应当能看见哪一步正在运行时，选择它。树按 agent 会话归属，与任务清单完全一致：子代理声明自己的计划就写自己的树，不存在共享或跨 agent 的作用域。当模型无法预先知道步骤时避免使用——每步都重写计划等于把任务清单换了个说法，而整树声明会为每次重写付费。

### 两个调用

`plan_write` 接收完整树并替换原有内容：没有部分写入，也没有逐节点编辑。每个节点带有全树唯一的 `id`、简短的祈使句 `title` 与 `status`；`detail` 与嵌套的 `children` 可选。`plan_step` 随后接收一个 `id` 和一个 `status`，因此一次状态变更只需一次很小的调用，而不是整棵树。两个工具都与 `subagent` 并行分派，模型应调用一次 `plan_write`，并在每次状态迁移时调用 `plan_step`。

两个调用都返回计数，模型无需回读即可看出剩余工作的形状。两个工具都会拒绝会让日志中记录的树失真的情形：空白或重复的 `id`、空白 `title`、未知 `status`、`plan_step` 指向当前树中不存在的 id、尚未做过任何声明就调用 `plan_step`，以及在没有归属 agent 会话时调用任一个工具。

### 投影

折叠结果以一个键发布，客户端通过普通的会话投影路径读取。

| 键 | 值 | 含义 |
|---|---|---|
| `planTree` | `PlanNode[] \| null` | 已声明并应用了所有被接受步骤的树；首次声明之前为 `null` |

该键同时由历史尾页与 `session/projection` 推送帧提供，因此打开或重新打开会话的浏览器无需自行重放日志即可拿到当前计划。

### 挂载

没有配置，因此一行装配就是全部设置；插件 `inject` 了 `tools` 与 `sessionProjections`，未挂载这两者的装配会让该行处于等待状态。

```yaml
- name: '@t4r71/dsh-plan-tree'
```

## 理解实现

<details>
<summary>实现内部细节——点击展开</summary>

本节解释两个工具背后的设计取舍，并指向实现它们的代码；可观察行为已在[使用本包](#use-this-package)中完整覆盖。

### 设计理念

三项承诺决定了本包的形状：

- **一次声明，之后逐步推进。** 昂贵且信息量大的调用是声明；高频的调用是只含两个字段的状态更新。把二者分开，能让常见操作在 token 与日志体积上都保持廉价。
- **仅记日志的状态，纯折叠。** 服务中不缓存任何东西。树通过折叠日志重建，因此恢复、fork 与压缩都能从当初产生计划的事件中恢复出同一个计划。
- **折叠即契约。** 对不属于自己的事件，`apply` 返回传入的状态引用，这正是框架的零工作量信号：长会话中一个无关事件不产生分配，也不触发下游重绘。

### 日志事件

两个事件承载全部信息。`plan/declared` 是整树快照，重放时后写覆盖先写，因此第二次声明会取代第一次而不是累积。`plan/step` 承载单个节点全树唯一的 `id` 与其新 `status`。两者都仅记日志：既可持久化又可重放，且都不会被组装进模型请求。

### 投影单元

该单元以 `init: () => null` 注册——在有任何声明之前，计划是"不存在"而非"空"。`apply` 在 `plan/declared` 时替换状态；在 `plan/step` 时只重建从根到目标节点的那条主干，若没有节点带有该 id 则返回原引用。`stateVersion` 为 `1`，wire 视图就是状态本身，因此客户端收到的树与折叠结果一致。

<a id="model-experience"></a>
## 模型体验

### 计划声明与步骤工具

#### 模型看到什么

无论计划处于什么状态，两个工具都常驻于每个请求：`plan_write` 接收完整的 `nodes` 树——每个节点有必需的、全树唯一的 `id`，必需的 `title`，以及必需且为 `pending`、`in_progress`、`completed`、`blocked` 之一的 `status`，另有可选的 `detail` 与 `children`；`plan_step` 则接收一个 `id` 与一个 `status`。成功声明返回 `total` 与各状态计数；成功的步骤返回节点的 `id`、新 `status` 与同样的计数。拒绝以失败的调用形式到达并指明出错的字段，因此模型会自我纠正，而不会悄悄偏离已记录的树。

#### Token 影响

包加载期间固定：请求的工具目录中有两个工具定义，另有每次调用的参数与结果留在会话历史中。只有模型确实重写整棵树时才会全额支付一次声明；一次状态变更只支付两个短字段，这正是长计划得以低成本保持最新的原因。

#### KV Cache 影响

无：工具定义不随计划状态变化，因此目录前缀保持稳定；一次状态变更只追加一个小事件，不重写既有上下文。折叠后的树本身从不进入请求——该投影只上到 wire——因此任何步骤都不会使可复用的前缀失效。

### 会话日志中的计划状态

#### 模型看到什么

不直接看到任何东西。`plan/declared` 与 `plan/step` 是仅记日志的事件，折叠出的 `planTree` 值流向浏览器载体而非请求。模型从它刚发出的 `plan_step` 调用的结果中得知步骤结果，而从不回读整棵树。

#### Token 影响

除写入事件的那几次调用之外没有额外开销。这里没有提示词段落、没有工具引导文本、也没有回读工具，因此声明计划并推进它的会话只为声明与步骤本身付费。

#### KV Cache 影响

无。由于该状态从不被组装进请求，声明计划、变更状态或在日志中已有计划的情况下恢复会话，都会让请求前缀保持逐字节一致。

## 已知限制与延期工作

<a id="known-limitations-and-deferred-work"></a>

- **只能整树声明** —— 树以整体方式声明；无法在不重述整棵树的前提下增删或重排单个节点，也没有回读工具。
- **不与执行耦合** —— 节点的 `status` 就是模型所说的状态。没有任何机制验证某个 `in_progress` 步骤仍在运行，被放弃的轮次留下的计划会保留其最后记录的状态。
- **id 的稳定性由模型负责** —— id 只校验全树唯一，不校验跨重写的稳定性，因此重新声明的树必须重复原有 id，步骤才能继续指向同一节点。
- **深度由渲染方负责** —— 嵌套的折叠与传输不限深度，真正绘制它的是边栏面板；病态深度的树是呈现问题，本包不做约束。
