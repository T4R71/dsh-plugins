# @t4r71/dsh-stream-guard

[English](README.md) | 中文

## 概述

当回答退化成填充内容——反复的宣告式短句，或同一句话循环数百字符——而你宁可切断重来也不愿它呈现在眼前时，挂载本包。它会在退化串被展示之前就将其移除，然后引导模型从最后一段实质内容继续，因此正在崩塌的回答仍能完成。它统计的是模型没有精确短语对应的反复意图接头，而不只是已知的填充语，也能对只是反复打转的最终回答发出提醒。代价是回答可能被缩短。`dsh` 基础组合包默认启用本包，无需接线。

<a id="use-this-package"></a>
## 使用本包

当模型偶尔在回答中途失去连贯性、用各种「宣告」代替收尾时，挂载此插件。无需接线：`dsh` 基础组合包已经运行它，默认值适用于大多数会话——想更早、更晚刹车，或让 reasoning 通道也受管时，调优下面的预算与通道即可。

### 何时选择

当长时间自主回答有时退化为填充语、且你宁愿截断并续写也不愿让这些凑字内容到达用户时，选择它。当模型必须完全不被干预时——guard 可能缩短回答——以及当「宣告式短行」本身就是交付物时（那正是检测器要抑制的东西），避免使用它。

### 设置预算与通道

想改变刹车何时触发或一轮允许续写多少次时，用配置挂载插件：

```yaml
- name: '@t4r71/dsh-stream-guard'
  config:
    brakeText: true            # brake a filler run in the visible answer
    brakeReasoning: false      # leave the reasoning lexicon alone (see below)
    cycleReasoning: true       # still catch a verbatim loop in reasoning
    cycleText: false           # do not hold the visible tail back for the cycle rule
    prefixReasoning: true      # count intent openings in reasoning
    prefixText: true           # count intent openings in the visible answer
    cycleHoldChars: 1024       # tail retained per channel while the cycle rule runs
    maxContinues: 2            # continuations steered per turn
    warnAfterContinues: 10     # warn past this many continuations (never a cap)
    maxHoldChars: 8192         # ceiling on characters held back per channel
    hesitationNudge: true      # nudge on hesitation churn
    hesitationBudget: 2        # nudges allowed per session
```

| 字段 | 默认值 | 含义 |
|---|---|---|
| `brakeText` | `true` | 对可见文本通道中已证实的填充语串刹车 |
| `brakeReasoning` | `false` | 对 reasoning 通道中已证实的填充语串刹车 |
| `cycleReasoning` | `true` | 在 reasoning 通道运行不依赖词表的循环规则 |
| `cycleText` | `false` | 在可见文本通道运行循环规则 |
| `prefixReasoning` | `true` | 在 reasoning 通道统计反复出现的意图接头 |
| `prefixText` | `true` | 在可见文本通道统计反复出现的意图接头 |
| `cycleHoldChars` | `1024` | 循环规则生效时每个通道保留的尾部字符数 |
| `maxContinues` | `2` | 刹车后每轮发出的续写提示数 |
| `warnAfterContinues` | `10` | 超过此续写次数后提示语附带警告（不是上限，永不停止续写） |
| `maxHoldChars` | `8192` | 每个通道扣住字符数的上限 |
| `hesitationNudge` | `true` | 对犹豫式反复输出注入请求侧提醒 |
| `hesitationBudget` | `2` | 每个会话允许的犹豫提醒数 |
| `verbose` | `false` | 通过 logger 输出刹车与提醒诊断 |

除非你已实测出需要改动的理由，否则保持 `brakeReasoning` 关闭。填充语词表读回答里的短行远比读 reasoning 可靠：在 reasoning 里，"Now." 这类行本身就是正常的连接词，词表会打在健康的思考上。循环规则是另一类证据，因此在 reasoning 上默认开启——数百字符长的逐字精确周期不是健康思考会做的事。`cycleHoldChars` 必须保持在 1024 以上，因为规则要等 `CYCLE_MIN_SPAN`（512）再加一个周期才能证实循环；更小的值会静默地禁用该规则，而不是让它更便宜。`cycleText` 关闭，是因为在可见通道上该规则的扣留是用户看得见的延迟，而词表已经覆盖了可见的崩塌。

`prefixReasoning` 与 `prefixText` 是上述所有扣留权衡的例外：它们**完全不付出扣留代价**。该规则判断的是已经完成的子句与行——一个已经到齐的子句开头，或一整行恰好只是一个填充词——因此它从不需要扣住任何文本就能得出结论，在两个通道上都不产生可见延迟。这正是两者都默认 `true` 的原因，也正是与 `cycleText` 的对照所在：循环规则是回溯性的，必须扣住尾部才能切除循环，而本规则只统计已经落定的接头。在可见通道上，反复的意图接头是比 reasoning 更弱的证据，所以两个通道各有独立开关；如果你自己的回答本来就大量以相同方式开启子句，把 `prefixText` 关掉即可。

无效配置会在启动时以清晰错误失败——例如超出文档范围的 `maxContinues: 999`——绝不会静默改变行为。生成的[配置目录](../../../docs/config-catalog.zh.md#deepseek-aidsh-stream-guard)记录每个受支持的值。

### 你会得到什么

文本通道上一连五行填充语会被抑制而非展示：其之前的文本保留，填充语串本身绝不发布，轮次带一条提示继续——指明输出停在哪里并禁止开场白。每轮与每会话预算约束这种恢复，因此反复崩塌的会话会停止被引导，转而正常结束，而不是陷入循环。另外，当已完成的回答呈现犹豫式反复——大量以「Hmm」「Wait」「Actually」或「等等」「不对」开头的短行——下一次请求会携带一条提醒，要求就现有最佳答案作出决定。注入文本的语言跟随对话自身的文字。干净的回答会逐字节原样通过，且不会触发提醒。

<a id="understand-the-implementation"></a>
## 理解实现

guard 注册在 `llm/stream` 上并包装 provider 流。每个通道（文本与 reasoning）拥有一个扣留缓冲区和三个检测器，分层是因为它们以覆盖范围换取速度。填充语词表逐行匹配已知的宣告式短语，能在数十个字符内触发，但只认它知道的那些短语。循环规则不依赖词表：它在保留的尾部中寻找逐字精确的周期，对任何重复内容都能触发，硬下限为 512 字符。接头计数规则数的是接头而不是行：以已知意图前缀开头**且**短到像一句宣告（不超过 18 字符）的子句，或整行恰好只是一个填充词，都会让计数器加一；两次接头之间只有非空白字符才计入 20 字符容差，一旦超出，计数器归零，因为模型又开始干实事了。容差内累计满 5 个接头即判定。长度上限是承重的，不是装饰——没有它，正常的规划长句会被当成接头；有它，本规则在 reasoning 语料上零误报。以每 delta 一个字符喂入退化形态实测：词表在 30–85 字符处触发，七种真实崩塌中漏掉五种；循环规则七种全中，但绝不会早于 512；接头计数在另两者完全看不到的形态上约 60 字符内即触发。三者合起来对健康的重复内容——300 行表格、普通散文、健康的开头后接实质内容——不动分毫。delta 送入每一个检测器，且只释放到已确认不含任一所标记候选的位置；从当前串起点起的内容全部留在缓冲区中。

这个扣留机制就是整个设计的关键。检测器需要证据才能证实一个串，而朴素实现早已把它流式发给了用户——而已发布的 delta 无法撤回，因为 `agent/assistant-stream` 实时发布，且已装配的消息由这些块定型。扣住尾部意味着触发阈值的串在判定发生时仍在缓冲区内，因此刹车丢弃的是从未发出的文本。没有任何内容需要「撤回」。

接头计数是唯一不参与这套扣留的检测器。它的证据是一个已经落定的接头，而不是一段需要切除的区间：一旦某个子句开头或某个纯填充词整行完整到齐，无需知道后面是什么就能让计数加一，而刹车不保留任何内容——既不发布前缀，也不丢弃文本。因此它的流式安全性来自「等待」而非「缓冲」：被 delta 切开的接头会保持待定，直到下一个字符给出结论，于是同一段文本在任何 delta 大小下计数一致。

恢复阶段还受两项约束塑造。流中途的截断无法就地续写：循环的重试阶梯只在 `error` 或 `aborted` 结束时触发，请求选项被深度冻结且由不变式强制 `options.messages === session.deriveMessages()`，而 assistant 消息由已装配的块定型。因此刹车关闭它截断的那些块、发出正常的 `stop`，续写则在 `agent/turn-stopping` 处引导——这使轮次保持存活，并在转录中带着续写提示运行另一个步骤。终结帧必须手工重建，因为流语法要求 `finish` 且禁止留下打开的块。

在工具调用处于打开状态时触发的判定会被放弃而非执行：半开的工具调用装配结果为空，因此在那里刹车会破坏该步骤而不是缩短回答。检测按通道、按流进行；预算按会话、按轮次计算。

#### 让被刹车的消息保持可回放

刹车改写了带提供方签名的文本，因此守卫会重建 replay 信封而不是放弃它——而两类签名的处理方式正好相反。

**文本**签名只是 `{v:1, id}`：它标出条目身份、不带文本，所以提供方从块本身取文本。因此上线的是被截断后的文本，条目原始 id 保持不变，缓存前缀在切割点之前仍然可读。

**reasoning** 签名是逐字回放的——提供方直接推送存下来的条目、完全忽略块自身的文本——所以原样带过去会把整段被抑制的循环重新送回线上，而转录却声称它已被移除。守卫会把这些签名的 `summary` 改写为它实际保留的文本。这个改写是忠实的而非编造的：在该提供方上 `summary` 与 reasoning 文本逐字节相同（1983 条签名实测：键集统一、无一携带 `encrypted_content` 块、`summary[0].text` 在每一例中都等于块文本），这既说明改写它是准确的，也说明守卫能判断出何时不该改。对于它未能完全识别的签名形态——包括携带不透明提供方块的那种——绝不猜测：改为丢弃信封，把这一条消息降级为提供方中立的历史。猜错的代价是静默地把循环重新送出去，那比丢掉条目 id 严格更糟。

<a id="model-experience"></a>
## 模型体验

### 刹车后的续写提示

#### 模型看到什么

填充语串被刹车后，下面这条被引导的续写消息会追加到转录中。当其前确有真实文本时，会在续写位置标签之后附加一小段，使模型在截断处续写而非重来。措辞跟随对话自身的文字——CJK 文字转录得到中文措辞，其余得到拉丁措辞，而无文字内容的转录回退到拉丁措辞，因为守卫绝不去猜一个它看不见的语言——因此下面同时记录两种实际发出的形式。

##### 续写提示（拉丁文字）

```markdown
Continue from where the text above was cut off. Do not repeat or restate what you have already written.

Where you stopped: …<tail of the last real text, up to 240 characters>
```

##### 续写提示（CJK 文字）

```markdown
从上面被截断的地方接着写。不要重复或复述已经写过的内容。

上次写到：…<tail of the last real text, up to 240 characters>
```

#### Token 影响

刹车发生前为零 token。每条续写都是该轮保留的历史记录，受每轮 `maxContinues` 约束（会话层不设上限，只按 `warnAfterContinues` 升级措辞）；附加的尾部上限为 240 字符。

#### KV Cache 影响

仅追加；新出现的内容位于可复用请求前缀之后，不会使现有 KV Cache 条目失效。

### 犹豫提醒

#### 模型看到什么

当已完成的回答呈现犹豫式反复时，下一次请求会携带下面的提醒。它绝不截断任何内容——等该模式可见时，这类反复输出早已写完。

##### 犹豫提醒（拉丁文字）

```markdown
You seem to be re-deriving the same conclusion. If you already have enough evidence, settle on it and continue; if you need more, say exactly what is missing.
```

##### 犹豫提醒（CJK 文字）

```markdown
你似乎在同一结论周围反复推导。如果已有足够证据，请收敛到结论并继续；如果还需要更多信息，请明确说明缺什么。
```

#### Token 影响

检测到反复输出前为零 token。每条提醒都会作为历史记录保留，受每会话 `hesitationBudget` 约束；每条不同的 assistant 消息最多触发一次提醒。

#### KV Cache 影响

仅追加；新出现的内容位于可复用请求前缀之后，不会使现有 KV Cache 条目失效。

## 已知限制与延期工作

<a id="known-limitations-and-deferred-work"></a>


这些限制说明 guard 何时不合适。它们是当前包约束，不是任务积压。

- **中文词表未经标定**——英文填充语族与犹豫比例是在 7,395–7,431 条真实健康样本上标定的；中文族是为覆盖面而补的，依据的是同样的意图而非计数。只有整行匹配才计入，且排除了普通中文话语标记，但中文流量上的误报率是未知的。
- **接头计数只认两种形态**——它统计以清单内意图前缀开头**且**不超过 18 字符的短子句（「Let me」「I need to」「让我」「接下来」等），以及整行恰好是一个填充词的行，后者来自一份刻意收窄的清单（「ok」「go」「now」「write」「emit」「here」「final」「writing」「producing」「emitting」，以及中文「好」「现在」「写」「输出」「生成」「写入」「接下去」「执行」）。不含这些接头的语义级重复——换个措辞重述同一结论、整句循环但从不以意图标记开头——仍然看不到。这就是诚实的边界：本规则抓的是失速模型的**口头习惯**，不是它的**含义**。
- **reasoning 不由填充语词表看守**——`brakeReasoning` 保持关闭，因为填充语词表读 reasoning 的效果很差：在 reasoning 里 "Now." 这类行本身就是正常的连接词，词表会打在健康的思考上。该通道改由循环规则与接头计数共同承担，而接头计数是两者中唯一能在 512 字符之前触发的。
- **行粒度的重复仍会漏掉**——循环规则要求逐字精确的字符周期。参考实现为它配了一条行级规则，本移植没有，因此那种每次措辞都变、却反复重述同样几行的崩塌不会被循环规则捕获；只有当这些行以清单内的接头开头时，接头计数才会抓到它。
- **循环规则无法在 512 字符以内的串上触发**——它需要这么多逐字重复才能证实该模式，所以立刻崩塌的模型仍会露出这么多退化内容。这正是接头计数（在另两者看不到的形态上 55–68 字符即触发）作为快层、而不是取代它的原因。
- **可见通道跑的是词表与接头计数，不是循环规则**——`cycleText` 保持关闭，是因为为循环规则扣留尾部会让实时流付出恒定的约 1024 字符延迟（实测：规则关闭时延迟 74 字符，开启时 1024 字符，对照 9,010 字符的健康散文）。词表在零显示代价下比循环规则早数千字符捕获同一次崩塌，而 `prefixText` 又在零显示代价下补上覆盖，因此循环规则被用在 reasoning 通道上——那里没人看流。
- **刹车可能缩短合理回答**——抑制正是其目的，续写是恢复手段，并不保证原文回来。
- **预算驻留内存**——每会话状态保存在内存中，重启后不保留，因此新进程从完整配额开始。
- **无法在流中途续写**——恢复总是跨越步骤边界；guard 无法在同一条流内重新请求。
- **工具调用打开期间的判定被丢弃而非延后**——该串会被释放且 guard 继续观察，因此那次崩塌不会被刹车。

<a id="dev-note"></a>
### 开发备注

<details>
<summary>维护者的工作上下文——点击展开</summary>

本开发备注是维护者的工作上下文：开放问题与尚未决定的探索方向。它明确不具权威性——已交付的行为、限制与既定理由以上文、包代码和相关说明为准。

检测器移植自 `ds-guard` 代理的 `src/guards/filler.rs`；扣留缓冲区与轮次边界续写是此处新增的，因为参考实现独占 socket 可以重新 POST，而 DSH 实时发布 delta、无法撤回。阈值在参考实现的真实语料上校准：犹豫比例 0.50 在 7,431 条健康样本中产生 9 次误报（0.12%），而 0.30 时为 38 次。每会话提醒上限之所以存在，是因为从转录中统计提醒标记时，连续 61 轮都报告「已提醒：0」。

循环规则移植自 `dsh-loop-guard` 参考实现的 `trailingCycle`。参考实现在每个通道上运行两条规则（`repeating-cycle` 与 `reasoning-lines`）；这里只移植了第一条，因此那些重复发生在行粒度、却没有逐字精确字符周期的崩塌仍未被捕获。参考实现还会立即 yield 每个块、只额外累积一份副本，所以它只能停止流、永远无法切除循环；这里的扣留机制才是让切除成为可能的东西。

接头计数规则取代了更早的 opener 规则（`src/opener.ts`，窗口 20 行、占比 0.8、至少 16 行），后者用行数与占比判断同一种失败。那个方向本身就是错的形态：用「接头计数 + 字符容差」才能触达 opener 规则完全漏掉的措辞漂移形态，而且在约 60 字符内就触达，循环规则却要等 512。opener 规则及其测试被删除，而不是与之并存。

词表是实测出来的，不是编的。在 2,159 个 reasoning 块、103,581 非空行上，有 23,371 行（22.56%）是接头——这些会话一直在剧烈退化，此前没有任何拦截。在语料中 1,469 个真正干活的块上，本规则触发 8 个，全部经人工核对为真死循环：触发块内接头占非空行的 36.7%–98.9%（最大的一个 115,071 字符块有 10,190 非空行，其中 10,082 行是接头，占 98.9%），触发处的 run 是 `Let me read.` / `OK.` / `Producing.` 之类。与同一规则的行级模拟在同一语料上对比，漏报为 0。按条目统计，`let me` 以 13,633 次命中遥遥领先，其后是 `ok` 2,738、`go` 2,593、`producing` 2,375、`writing` 1,585、`i'll` 141、`让我` 96、`now` 55，其余均低于 50。语料中出现但属正常行文的接头——`实际上`、`所以`、`等等`、`另外`、`嗯`、`好，`、`如果`、`或者`——被刻意排除，因为纳入它们会打在健康的行文上。语料随工作推进一直在增长，所以从中读出的触发块数是会漂移的：可复现的数字是漏报率为 0，而不是块数。开发这些会话本身被排除在「真正干活」的数字之外，因为其中的模型正在**写填充词本身**——引用本插件自己的夹具、把 `OK` / `好。执行。` 当作测试数据逐行列出——它触发规则的原因与模型是否陷入循环毫无关系。

对词表的两处限制是刻意的，不要再放宽。第一处是整行填充词清单：它冻结为原版 `FILLER_ONEWORD` 族（`src/guards/filler.rs:42-53`）——拉丁侧 `ok`/`go`/`now`/`write`/`emit`/`here`/`final`/`writing`/`producing`/`emitting`，中文侧 `好`/`现在`/`写`/`输出`/`生成`/`写入`/`接下去`/`执行`。曾试加 `output`/`continue`/`done`/`execute`/`executing` 并已回退：它们只多换来一个触发块，而那个块是误报——模型在写测试代码，在围栏样例里把填充词当数据列了出来。参考实现自己的注释就警告过这一点，说这份清单刻意收窄，因为更松的规则「会打在 `Name` / `core` / `dsh` 这类列表输出上」。中文的 `输出` 保留：它属于中文对应族，实测新增 0 误报。第二处是意图前缀的 18 字符上限。它是承重的，不是装饰：扫描 102,936 行，被判为填充语的行数在 12 字符时为 6,597、14 为 13,008、16 为 13,497、18 为 13,565——而这些档位新增收进来的真实工作样本都是 0——之后跳到 20 的 13,579、24 的 13,582 并在那里饱和，且每一档越过 18 都会收进 `Let me verify that.`、`Let me implement that.` 这类真正的规划文本。完全去掉上限则会把普通长推理一扫而入，其中有 11,471 行只是以意图前缀开头、实属正常内容。

切割处的两个缺陷是通过测量刹车**保留了什么**发现的，而不是看它是否触发——两者都无法从通过/失败中看出。第一个：`span` 等于 `max(minSpan, 2 * period)`，而这个恒等式被所有不超过 `minSpan / 2` 的周期满足，因此由它反推周期，对任何短周期都会返回 2 或 3，切割点便落在重复内部；现在扫描直接报告它真正匹配到的周期。第二个是数据丢失：`runStart` 兼任释放游标，而行扫描器只为已换行的行推进它，于是未终止的缓冲区把切割点钉在 0，丢弃了循环之前的全部内容——一段真实的 34 字符回答后接无换行循环时，保留了 0 个字符。两者都有回归测试。

开放问题，均未决定。既然签名现在可以被改写，reasoning 词表是否还应保持关闭——改写移除了它当初关闭的理由，剩下的只是「reasoning 中的填充语是否值得作为证据行动」这个问题。以及参考实现中的 `containment`（跨调用复述度量）在这里没有对应实现。`cycleText` 的问题现在已由测量回答、不再是开放问题：恒定的约 1024 字符可见延迟（9,010 字符健康散文上从 74 升至 1024）换来一条词表本就比它早数千字符到达崩塌的规则，因此保持关闭。只有在真实可见崩塌被实测出词表漏掉时才重新考虑。
