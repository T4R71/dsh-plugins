## 四、自指伪影：真实负载 8 / 自研会话 23

**这是本次复核最重要的发现，也是不能直接报「0 误报」的原因。**

语料是**活的**，而**本次任务自身就在往语料里写**。两次连跑之间块数就会变
（实测 2234 → 2244 → 2258 → 2278），因为 M-ds-guard 下的会话正在被实时写入。

按**会话级**切分（会话全文提及 `stream-guard` / `PrefixGuard` / `FILLER_WORDS` /
`DESIGN-prefix` / `接头` 等内部词汇 → 自研究会话）：

| 类别 | 会话 | reasoning 块 | 触发 |
|---|---|---|---|
| 自研究会话 | 10 / 76 | 809 | **23** ← 自指伪影 |
| 非自研究会话（真实负载） | 66 / 76 | 1469 | **8** ← 真死循环 |

自研究会话里，模型在**写/引用填充词本身**，例如：

- **块 #1618（`cacc14b5…`）**——模型正在复核我这份工作，原文引用了 `好。执行。` 夹具：
  ```
  "Note blocks #13-#18 look concerning: they show "接头行 0 行" (0 joint lines) yet fired with 5 joints…"
  "Block #14: line L4: "`好。执行。好。执行。...好。执行。好。行。好。执行。`"" — that contains literal repeated "好。执行。"
  ```
- **块 #1620**——模型自己指出这就是 DESIGN §3.4 警告的形态：
  ```
  "That's exactly the "writing test data" false-positive shape that §3.4 warned about!"
  ```
- **块 #1629（`ec54776e…`）**——模型在**设计 `OK` / `<20 chars>` / `OK` 的容差测试用例**，
  代码块里逐行列出填充词，于是被表 B 逐行命中。

**这正是 DESIGN §3.4 记录的失败模式**（「模型在写测试代码，代码块里列了填充词作为测试数据」）。
它不是规则在真实工作负载上的缺陷，而是**测试/开发这条规则本身**时的自指伪影 ——
一个正在被开发中的守卫，其开发会话必然包含它的测试夹具。

**处理建议**（供 Lead 决策，不在本次写入范围内）：`tests/verification/CORPUS.md` 结论中报
「真实负载 0 误报」，并显式排除自研会话；同时建议在正式基准中固定一份
**时间截止的语料快照**（本文件给出 `CORPUS_CUTOFF` 开关），否则任何数字都会随会话增长而漂移。

## 六、交付结论

1. **真死循环仍被抓住** —— 合成 8/8 不漏；真实负载 8 块全部人工核对为真死循环；
   基线行级模拟抓到的块最终实现**一个都没漏**（交集 8/8，漏报 0）。
2. **误报 = 0** —— 真实工作负载 1469 个 reasoning 块中触发 8 块，全部为真死循环；
   健康文本（合成 6 例 + 真实语料 1461 块）零触发。
3. **对基线「17」的判定：不能确认，应予修正。** 17 是行级模拟值（非真 PrefixGuard），
   同口径重跑当前语料为 19；真正的承重指标是**漏报 0**，已满足。
4. **必须披露**：语料总触发 31 块中有 23 块来自**正在开发本规则的自研会话**
   （自指伪影），与 DESIGN §3.4 警告的形态同源。报数时应按会话切分，并固定语料快照。
