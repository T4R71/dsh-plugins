## 3. 已实测确认的事实（可引用，脚本可复现）

### 3.1 跨通道复读分布（**已独立复现两次**）

```
语料：$DSH_HOME/sessions/**/session.v3.jsonl.zstd
筛 reasoning >= 1500 字符 -> 约 1446 条
8-gram Jaccard(reasoning, text) 直方图：
   0- 5% : 1426    5-10% : 11    10-15% : 1    95-100% : 8
   15%–95% 之间：0 条（干净空带）
```
不同度量下空带位置不同：Jaccard 与 `|A∩B|/|A|` 有 15–95% 空带；
`|A∩B|/|B|` **连续分布到 75%**，没有空带。
→ **主判据只能用 `|A∩B|/|A|` 方向。**

### 3.2 灾难样本的污染情况（**关键**）

8 条灾难样本中**只有 2–3 条真正独立**：

```
b923ce6b      120036  cwd=M:\Codex\.codex  origin=subagent depth=1  <- 不是顶层会话
session-d531c71b 115071  cwd=M:\Codex\.codex  depth=0              <- 独立
session-3ef35930  7155  cwd=...Downloads\Noname v1.6.6            <- 独立
97a12893 / 928ba8fe / ec54776e / session-d50364e9  <- 全部来自 --M-ds-guard-- 自研究会话（污染）
```

**判定污染要看 `origin` / `delegationDepth` / `parentSession`，不能只看关键词**。
关键词法会误判：`restate` 是英文常用词，4 条候选全部命中它。

### 3.3 第一层延迟与失明（真实代码实测）

```

填充语洪流 (Let me write.×N)      49 字符      48 字符

灾难性复制 (长行正文复制)         -1 (失明)    -1 (失明)
```

**现有三条规则对灾难复制形态 100% 失明** —— 这是重构的动机。脚本 `latency-probe.mts`。

## 4. 已证伪的结论（**不要再提这些方案**）

### 4.1 ❌ `echoR + coverT + MATCH_FLOOR` 跨通道判据 —— 已证伪

**不要重新提出它。** 它无法区分「灾难复制」与「模型忠实把推理写进正文」：

```
健康形态：正文逐句复述 reasoning（16 句各不相同，不是循环）
  echoR=1.0000  coverT=0.8735  matched=1040  -> 触发
```
**证伪机制**：`matched = coverT × len(text)` **不是独立于 `echoR` 的轴** ——
正文越长越合法，两者同时上升。扫 floor 0→512，健康集最大 `echoR` 从未低于 0.9904。
**这根轴不存在。**

### 4.2 ❌ 「不区分正文/推理，只看合并流」—— 实测更差

```
口径                  灾难召回    健康误报
合并流                 1/4        38/1450
只看 reasoning         1/4        36/1450
只看 text              1/4         5/1450   <- 最好
```
合并**不提升召回**，误报却涨 7 倍。reasoning 本就该高频出现 `Let me`（草稿空间），
合并后它的噪声污染整条流。**保留分通道。**

### 4.3 ❌ 「中间字符过短 → 连续 5 次」单独不成立

```
阈值 run>=5 (gap<=20)：触发 41/1454 = 2.8%
触发样本多数长这样：lenR=51211 lenT=0   （纯推理、正文为空）
```
**「间隔短」≠「空转」。** 健康推理写「Let me check X. The result is Y.」时，
前缀之间的内容**短但每次都是新的**。→ **要看「重复」，不是看「间隔」。**

### 4.4 ❌ 字符层周期（`trailingCycle`）看不见短语池循环

官方 README 记录：330k 字符的短语池循环，周期上限从 64 试到 4096 **全部返回 0**。
在我实测的 115k 洪流上，字符层只看见 `period=53 span=618`（局部），
而**行层看见 10190 行 / 118 个不同行**的完整退化。
**量错了「层」，不是上限太小。** 这也是规则 B 应当退休的理由。

### 4.5 ❌ 用「一个统计量」统一两种病 —— 全部失败

灾难其实是**两种不同的病**（§5.0），必须两条规则。实测过的单一统计量：

```
候选单一统计量            结果
合并流 maxCount>=T        模式 2 完全看不见（那些块 maxCount 只有 2~21，与健康块重叠）
合并流 dupFrac>=T         最多 8/11，模式 1 里 3 个只有 0.07~0.25
合并流滑动窗 freq>=T      最多 5/11，同时 8~20 个健康误报
```

### 4.6 ❌ 数字掩码（`\d+ -> #`）—— 有害无益

真实语料上**多找出 0 个循环**，却让枚举列表 / 日志 / 表格**全部误报**。
（`Step 1`、`Step 2` 掩码后变成同一行。）**标签不要掩码数字。**

### 4.7 ❌ 滑动窗口 freq 比累积 freq 好 —— 反了

```
累积 freq>=4    触发 5/11   健康误报 0    健康最大 2.664
窗口 W=40       触发 5/11   健康误报 10   健康最大 10.000
```
累积量**更简单也更安全**。（窗口的用途是防稀释，但本语料没观测到稀释漏报。）

### 4.9 ✅ R1 与「犹豫 churn」的冲突面（**本轮实测，重要**）

R1 上线后打挂了 2 个 hesitation-nudge 测试。**这是真缺陷，不是测试问题。**

```
churn 形态                          R1 是否触发
'Wait, that is wrong.' x10 (209字符)   不触发（低于 REPEAT_MIN_LINES）
'Wait, that is wrong.' x40 (839字符)   触发   <- 与 hesitation 规则抢同一形态
措辞变化的 churn（真实形态）            不触发（重复度=1）
```

**判定依据来自真实语料**：统计全部 text 块中「连续完全相同行」的最长游程，
**全语料最大只有 4**。真实 churn 会**换措辞**（`Hmm` → `Wait` → `Actually`），
不会把同一句话原样重复 40 次。

→ **40 行逐字相同确实「无法终止」，R1 触发是正确的**；
  短 churn（<32 行）交给 `hesitation.ts` 去 nudge（它只看 60 行窗口、8 行即判）。
→ **`REPEAT_MIN_LINES = 8` 改为 32**：高于 10 行 churn 3.2 倍，低于最小真阳性
  （150 行）4.7 倍，两侧余量都很大。

**同时证伪了「再加一条字符下限」**：二维网格搜索显示没有任何 `(minLines, minChars)`
组合能同时「拒绝任意规模的 churn」且「保住 150 行的真阳性」——
256 行 churn（5375 字符）本身就重于 2560 字符的真阳性。
但那个规模不需要网关：`judgeHesitation` 早在 8 行时就会先接管并 steer。

### 4.10 ⚠️ 「合法长引用」不是盲区，是可测的（**本轮纠正**）

我上一轮把它写成「无法测试的盲区」，人类质疑「不能补充测试吗」——**质疑是对的。**
该形态完全可以**生成**，于是边界被测试固定下来：

```
引用形态                                      R2 是否触发
引用行全部在前、后面接正文（18 行引用）          触发   <- 18 行连续逐字推理就是病态
引用与正文**交错**（真实形态），引用占比 <= 0.88  不触发
引用与正文交错，占比 0.95（60 行里 57 行）      触发   <- 已经不是「引用」了
中文引用 50 行 + 10 行新正文                    不触发
```

**关键教训（时基陷阱的第二次出现）**：R2 判的是**流式进行中的比例**，不是整块终值。
同一个终值 0.3 的块，「引用在前」会触发、「交错」不会。
**用整块终值给流式判据写测试，会得出错误结论。**

### 4.8 ⚠️ 我自己犯过的错（引以为戒）

- 移植 `trailingCycle` 时**漏掉了 `new Set(template).size < 2` 守卫**，
  导致「1438/1438 全触发」的荒谬结果。**移植必须逐字核对，不能凭理解重写。**
- **做了不对等比较**：行回声用「整块终值」而 8-gram 用「流式前缀最大值」，
  得出「行级间隔 0.30 vs 8-gram 0.13」。同口径重测后是 **0.186 vs 0.133**。
  **比较两个判据时，必须先把「求值时点」对齐。**
- 把「config 引用误报 echoR=0.58–0.76」报高了（真实形态只有 0.1444）——
  那是人造的、reasoning 本身高重复的对照。**对照必须是真实形态。**
- 说「L=8 就触发」不准确（自然文本约 93），那是重复单元缓冲的极端情形。
- 阈值扫描时把**正样本混进了「健康最大值」**，得出「健康最大=1.000」的荒谬结论。
  **算健康基线前必须先扣掉已知正样本。**

## 5. ✅ 最终验证通过的方案（最小化版本）

### 5.0 最重要的发现：灾难是**两种不同的病**

这是上一版方案翻车（§4.1）的根因 —— 我一直试图用**一个**判据同时抓两种病。

```
模式 1  内部循环     推理自己反复说同样的话
        d531c71b  115071 字符 / 10190 行 / 只有 118 个不同行  （重复度 87）
        7858b9d6   51211 字符 /  2753 行 / 只有 356 个不同行  （重复度 7.9）

模式 2  跨通道复读   正文逐字复述推理
        928ba8fe  推理 116081 / 正文 116079   行回声 = 1.000
        97a12893  推理 119312 / 正文 119310   行回声 = 1.000
        ec54776e  推理 109217 / 正文 109215   行回声 = 1.000
```

实测交集与并集：**只有模式1 = 3 个；只有模式2 = 6 个；两者都有 = 2 个；并集 11 个。**

**两种病必须两条规则。**（用单一统计量统一的尝试全部失败，见 §4.5）

### 5.1 第二层：两条各自只是一个除法/求交的规则

```
R1 内部重复   重复度 = 行数 / 不同行标签数 >= 4

R2 跨通道复读 推理行集合 R = Set(推理行标签)
              正文行逐个到达，hit = 命中 R 的行数，seen = 正文行数
              seen >= 4 且 hit/seen >= 0.9  ->  熔断

行标签 = trim -> 小写 -> 去行尾标点 -> 合并空白      （**不要掩码数字**，见 §4.6）
```

实测（真实语料 1656 块，脚本 `tests/verification/verify-two-layer.mts`）：

```
R1 触发 5 个块   健康最大重复度 2.658       阈值 4 余量 1.5 倍
R2 触发 8 个块   健康最大前缀行回声 0.714   阈值 0.9 余量 0.186
合计 11 / 1656 = 0.66%，逐个核对全部是真循环或真复读
R2 最迟在正文第 897 字符判定（预算 1024）
R2 判定点与输入分块大小无关（1 / 64 / 4096 字符完全一致）
```

### 5.2 两层都**不需要扣留（holdback）** —— 本版最大的简化

上一版为字符层周期设计了扣留/释放游标，代价是**恒定 1024 字符可见延迟**
（60 字符/秒下首字要等约 17 秒，1024 字符以下的回答全程不可见）。

**R1 和 R2 都是单调判据**：只对**已收到的内容**判定，成立即刻熔断，
不需要回撤任何已发出的字符。于是整套扣留机制可以删掉。

**1024 是判定时限，不是扣留窗口。**

### 5.3 R1 有一条数学保证（值得写进代码注释）

重复度 = (H+L)/(H+d)，H=健康行数，L=循环行数，d=循环不同行数。
要它 >= 4 即 **L >= 3H + 4d**。只要循环**不自己停止**，L 无限增长，
**重复度必然最终越过 4**。即 R1 对任何不终止的循环**一定会触发**，只是早晚。

已实测的副作用：超长健康前缀会稀释（需循环篇幅约为健康篇幅 3 倍）。
真实灾难块里 R1 分别在 1949 / 8988 / 10661 / 22707 / 34979 字符触发，
但**那不是检测慢** —— 循环内容本身就从那里才开始。真正的反应延迟是 225~389 字符。

### 5.4 只移植 loop-guard 的一条判据

仓库 `https://github.com/MrWeiCodes/dsh-loop-guard`（MIT，v1.0.3）：

| 资产 | 移植 | 为什么 |
|---|---|---|
| 集中度判据（行数/不同行数 >= 4） | ✅ | **这就是 R1**，735 会话标定过 |
| `LINE_MIN_CHARS = 2` | ✅ | 「`}`/`);` 会合法重复上百次」的护栏 |
| 标定注释与理由 | ✅ | 从代码本身看不出来的踩坑信息 |
| `trailingCycle` / `periodicTailSpan` | ❌ | 字符层，对短语池循环失明（§4.4） |
| 终结算子 / `resumeAfterBreak` | ❌ | 本包已有更成熟的路径，不降级 |
| `cordis.patch.yml` / 插件加载 | ❌ | **不引入依赖**（人类硬约束 H1） |
| `LoopDetector`（跨调用） | ⚠️ 暂缓 | 管「连续 N 次停滞调用」，是 turn 级语义 |

**结论：真正要移植的只有一条判据 —— 行数/不同行数 >= 4。**

## 6. 「99.9% 命中率」的诚实结论

**当前语料在统计上不可能支撑这个数字。**

```
零漏报 n 次下的精确单边 95% 置信下界：
   n=2   -> 22.4%      <- 真正独立的顶成正样本数
   n=3   -> 36.8%
   n=8   -> 68.8%
   n=100 -> 97.0%
   n=2995 -> 99.9%     <- 要宣称 99.9% 所需的最少样本
```

**分母是无法回避的难点**：那 8 条正样本全都是**被判据本身**（echoR≥0.9）找出来的 —— 循环论证。

**建议的验收口径（双层）**：
- **定义 A（真实语料）**：2/2 或 3/3 全部触发，**但必须同时报告 95% 下界**，不得只报 100%。
- **定义 B（生成器）**：≥3000 条参数化合成洪流，**0 漏报**，且每条 ≤1024 字符内触发。
  生成器**必须包含「合法长引用」健康对照**。
  ⚠️ 早先这里写「真实语料里几乎没有这种形态，是个盲区」——**已证伪并纠正**：
  它不是盲区，可以**生成**，边界已在 `tests/echo.spec.ts` 里逐点固定（见 §4.10）。
  真实语料里少见，不等于不可测；把「样本少」说成「测不了」是偷懒。

## 7. 环境与工具链的坑（Windows）

| 坑 | 正确做法 |
|---|---|
| 会话日志是**多帧** zstd | 按 magic `28 b5 2f fd` 切帧，逐帧 `zlib.zstdDecompressSync`（**不是** `inflateSync`） |
| reasoning 文本路径 | `e.type==='assistant/message'` → `.data.message.content[].type==='reasoning'` 的 `.text` |
| `npx tsx` 里的绝对路径 import | 会报 `ERR_UNSUPPORTED_ESM_URL_SCHEME`（`m:` 不是合法 scheme）<br>→ **把脚本放进仓库内**用相对路径 import |
| 逐字符喂 PrefixGuard | O(n²)，实测 622 秒被中断 → **用 64 字符分块** |
| 语料是**活的** | 会话在持续写入，两次运行数字会变（1446→1449）→ 需要时先冻结快照并记 sha256 |
| oxlint | 禁 `!` 非空断言、禁 `[...str]`（用 `Array.from`）、无行尾空格 |
| 覆盖率门禁 | `vitest.config.ts:356` `perFile:true` 四项 100% → **每个新分支都要有测试** |
| 改完 `src` | 必须跑 `pnpm run build:lib:host`（exit 0）才生效 |

- **先读代码，再信简报。** 简报里的数字可能与源码不符。

  `origin`/`delegationDepth`/`parentSession`，不能只看内容关键词。
- **合并规则时，除了阈值还要清点「策略」**：通道开关、否决条件、优先级。
  见 §10.2 —— 我正是因为只盯着阈值，把 `brakeReasoning` 一起合并没了。

## 10. 本轮落地的实现与新增教训（两层重构收尾）

### 10.1 代码现状 [实测]

`src/` 现为 **9 个文件**，探测类 **2 层 3 条规则**：

| 位置 | 文件 | 作用 |
|---|---|---|
| 第一层 | `announce.ts` | 合并后的「宣告」计数器：filler 词表 + intent 前缀，**一个计数器两种命中** |
| 第二层 R1 | `repeat.ts` | 通道自我复读：`行数 / 去重行数 >= 4`，且 `>= 32` 行 |
| 第二层 R2 | `echo.ts` | 正文复述推理：`>= 0.9` 且正文 `>= 8` 行 |
| 支撑 | `text.ts` | 从 `filler.ts` 抽出的共享助手（`textLen`/`isBenign`/`MAX_SHORT_LINE`） |
| 支撑 | `hesitation.ts` `signature.ts` `language.ts` `wording.ts` | 复用不改 |
| 装配 | `index.ts` | 三个 guard + 零扣留流循环 + `agent/turn-stopping` |

**已删除**：`cycle.ts`、`filler.ts`、`prefix.ts`（连同字符周期规则与整套扣留机制）。
**配置开关 13 -> 10**；内部探测常量 15 -> 8。

### 10.2 ⚠️ 本轮最重要的教训：合并规则时**把通道策略一起丢了**

这是一个我自己造出来、又自己测出来的**真实回归**，值得单独记下来。

老设计里 filler 词表在 reasoning 通道上是**被否决**的（`brakeReasoning: false`），
源码注释写明了两个理由：reasoning 块带 replay signature，截断会让下一个请求丢掉
passback 状态；而且私有草稿里的 `Writing.` 比用户读到的正文里的同一个词弱得多。

我把 A（filler）和 C（intent）合并成一个计数器时，把这条通道策略**一起删掉了**。
结果：

- 合并后命中 **35** 个通道块（reasoning 上 32 个）。
- 其中 **20 个是 filler 完成的**，也就是老设计明确否决的那一类，
  包括一个 **109,217 字**的 reasoning 块。
- 全量语料（1675 块）总命中从 11 涨到 **37**。

**修法（最小）**：合并没有错，丢策略才是错。`AnnounceVerdict` 本来就带 `kind`，
用它就行 —— `index.ts` 恢复为 `target === 'text' || brakeReasoning || av.kind === 'intent'`。
计数器**不重置**：这条 run 是真实存在的，不同的是**处置方式**，
之后任意一个 intent 命中仍会正常熔断同一条 run。

修复后 [实测]：全量语料总命中 **18**（`echo` 6 / `repeat` 5 / `announce-intent` 7），
**filler-on-reasoning 归零**。

> **教训**：把两条规则合并成一条时，要逐个检查被合并掉的**不是阈值**的那些东西 ——
> 通道开关、否决条件、优先级。阈值看得见，策略看不见。

### 10.3 零扣留带来的两个连带改动 [实测]

1. **没有 resume anchor 了。** 老 guard 会把保留的前缀附在续写提示后面当锚点；
   现在什么都不缓存，所以提示就是纯粹的 `wording.continue`。
   `tests/evidence.spec.ts` 的两条断言据此重写：现在断言提示**不含**答案正文，
   且正好是那句续写指令。
2. **熔断摘要换了格式。** 从 `braked (filler|cycle) on <ch> ... kept N chars`
   变为 `braked (announce|repeat|echo) on <ch> (N announcements | N lines restated |
   N lines, M distinct)`。`kept` 这个词被删掉是**故意的** —— 没有任何东西被扣留，
   写 `kept` 就是在描述一个不存在的量。

### 10.4 测试迁移 [实测]

- `tests/prefix.spec.ts` -> `tests/announce.spec.ts`：纯符号改名
  （`PrefixGuard`->`AnnounceGuard`、`PREFIX_TOLERANCE`->`ANNOUNCE_GAP`、
  `PREFIX_COUNT_LIMIT`->`ANNOUNCE_COUNT`、`LETME_MAX`->`ANNOUNCE_MAX`），
  **99 例全绿**，没有为迁就实现而放宽任何断言。
- ⚠️ **操作事故（已恢复）**：我用 PowerShell 一行做「读原文件 -> 改名 -> 删原文件」时，
  `Set-Content` 把新内容写到了别处，结果**先删后写失败，`prefix.spec.ts` 一度丢失**。
  靠**早先 `git add` 过的索引**用 `git show :<path>` 完整恢复。
  **教训：破坏性文件操作要先把内容读进变量并确认写入成功，再删原文件；**
  **未提交的新文件必须先进 git 索引，否则一次手滑就没了。**
- ⚠️ **PowerShell 坑**：`[System.IO.File]::ReadAllText(相对路径)` 解析的是
  **进程工作目录**（`M:\ds-guard`），不是 PowerShell 的 `cd` 之后的目录；
  内容里含反引号时 `Set-Content -Value` 的位置绑定也会错乱。
  跨目录文件操作请用**绝对路径**，或干脆用 read/write 工具。

### 10.5 收尾：覆盖率与两处「不可达分支」的判断 [实测]

最终验收：**236 测试全绿**，10 个源文件 **per-file 100% 覆盖率**（四项全 100%），
`oxlint` 0 error，`tsc -b tsconfig.host.json` exit 0，`pnpm run build:lib:host` exit 0，
文档门禁通过。

补齐覆盖率时遇到两处**真·不可达分支**，处理方式不同，值得记下来：

1. **`signature.ts` 的 `partType ?? SUMMARY_TEXT`** —— 死代码，根因是**两处检查重复**：
   第 105 行已经拒了空数组，循环必然至少跑一次，每次不 return 的分支都已证明 `type` 是
   string，所以 `??` 右操作数永远不执行。
   **修法是删冗余而不是加测试**：把空数组判定折进循环后那一次 `partType === undefined`
   判定，语义完全不变，分支重新变活，`SUMMARY_TEXT` 常量一并删除。
   > 教训：**不可达分支往往不是缺测试，而是代码里有两条互相覆盖的检查。**

2. **`index.ts:478` 的 `if (kind !== 'text' && kind !== 'reasoning') continue`** ——
   守卫是防御性的，不变量（`braked` ⇒ `open` 里只有 text/reasoning）**横跨两个函数**，
   删掉它会让未来改动 `blocking()` 的人失去保护。这里用
   `/* v8 ignore next -- <理由> */` 标注 —— 仓库有 **93 处**同样做法，是既定惯例。
   > 教训：**同样是不可达，能靠去重重构解决的就重构；跨函数不变量则标注并写清理由。**

⚠️ 写 `v8 ignore` 注释时注意 `@stylistic(max-len)` 上限是 **140 字符**：
长理由要拆成普通多行注释放上面，`v8 ignore` 那行只留一句短理由。

### 10.6 对话「截断」的真正原因 [实测]

不是上下文窗口太小（**262,144 tokens**，见 `llm-pi-ai/src/config.ts:64`），
而是**单次回复输出上限 32,768 tokens**（同文件 `:67` 的 `DEFAULT_MAX_TOKENS`）。
`settings.yaml` 未覆盖 `maxTokens`，catalog 也没有 `deepseek-flash` 条目。
单轮里塞大段代码 + 长文 + 几十次工具调用就会顶到这个上限被硬切。
[推测] 推理 token 通常同计一个预算，故长篇思考也在消耗它 —— 未实测。

### 10.7 turn 以宣告式正文结束：PTC 无效应，不新增规则 [实测]

问题：PTC（模型用 `run_code` 派发工具）是否比非 PTC 更容易出现「turn 无 tool call 结束 +
正文宣告下一步却不做」。全量审计见 `tests/verification/DEGENERATION-AUDIT.md`。

- 基线：412 个有 assistant 消息的 turn 里 **92.2%** 以无 tool call 结束 —— **这是正常结局**，
  且比例不随上下文规模上升，故也不支持「长上下文导致退化」。
- 大规模正文复读（剥围栏代码块，≥20×）：PTC 1、非 PTC 1，**各 1 例，无差异证据**。
- 两个灾难样本 `"Let me read."`×6110 与 `"Producing."`×2012 **都被现有规则在默认阈值命中**
  （均 `announce/intent`，均 count=5）→ 现有规则集在真实退化上有效。
- **决定：不新增 turn 级判据。** 根级统计是负结果 + 灾难已被覆盖 + `ASKS_USER` 排除表未经
  标定且已有 1 例误报 + 最小化原则。

#### 统计单元必须按根对话，不能按会话文件 [实测]

⚠️ 本节第一版是**错的**，错误在统计单元。89 个会话文件里 **53 个是子代理**；按
`parentSession` 重建谱系后只有 **36 个根对话**。子代理的输入由父对话决定，**不是独立抽样**，
把它们当独立观测会人为放大有效 n：

| 统计单元 | PTC | 非 PTC | 检验 |
|---|---|---|---|
| 会话文件（错误） | 9.7%（11/113） | 1.1%（3/266） | 置换 p=0.0585 |
| **根对话（正确）** | **4.2%（11/263）** | **2.4%（3/126）** | **置换 p=0.9503** |

根级 p=0.95 表示观察到的 1.8pp 差异**比随机打乱标签的典型差异还小** —— 即**无效应**。
决定性证据是 PTC 组内部异质性：4 个 PTC 根中 `0/159` 与 `7/56` 并存，**标签不预测行为**。

做法：会话首个事件带 `parentSession` / `origin` / `delegationDepth`，据此 `rootOf()` 上溯。
⚠️ 记数仍有上限不确定性：日志给出 4 个 PTC 根，操作者按自身使用计数为 **2 个**
（agent-team 的 teammate 可能不记录 `parentSession`）。4 个 PTC 根**全部**带 agent-team 标记，
且非 PTC 组也有 3 个带标记 —— **「PTC」与「agent-team」本轮无法分离**。

⚠️ **探针的结构必须与插件、与数据的真实结构逐行对齐，否则输出不是证据。** 本轮错了六次：

1. **统计单元错误**（最严重）→ 把子代理会话当独立观测，得出「PTC 高 9 倍」的假象。
   先按 `parentSession` 重建根对话谱系，再比较。
2. 在**对话正文**里匹配规则名 → 得出 775 条「触发」，实际只有 **5** 条。
   真实通知要按 `type==='user/message'` + `source.plugin==='stream-guard'` 结构化匹配。
3. **跨通道共用 guard 实例** → 造出 20 条插件不可能产生的 `announce/filler on reasoning`。
   插件是每通道独立实例（`announces[channel]`）。
4. **把 markdown 结构当退化** → `"|---|---|"`、`"```ts"` 占 4/5 命中，必须先剥围栏代码块。
5. **正则要求宣告位于绝对末尾** → 漏掉全部以 `。` 结尾的宣告，发生率被低估到 0.3%。
6. **Fisher 的分母边际写错**（`c+d-a+k` 应为 `d-a+k`）→ 返回 p=1.0000。
   用 `fisher-check.mts` 的两个已知答案自检后才可用：**检验本身也要有已知答案的测试。**

同一类错误（早期）还有：「整块口径 ≠ 流式口径」—— 一次性喂整段文本与逐 delta 喂，
`AnnounceGuard` 看到的分句结构不同，结论也不同。**测量前先问：我的口径和插件的口径一致吗？**
