# 两层检测架构重构方案（PLAN-two-layer）

> 本版按「**最小化原则**」重写：一个能用**一个数/一次查表**表达的判据，绝不用三个。
> 上一版的 8-gram + coverT + MATCH_FLOOR 三段式判据**已被实测证伪**，见 §4.3、§12。

---

## 0. 最终结论（先读这段）

> **实施状态（本轮更新）**：第二层 **R1 / R2 已落地**，见 `src/repeat.ts`、`src/echo.ts`，
> 接入 `src/index.ts`，新增开关 `repeatGuard` / `echoGuard`。
> 两者 **100% 覆盖率**，包内 **229 测试全绿**，`oxlint` / `tsc` / `build:lib:host` 全部通过。
> **第一层的 A+C 合并与规则 B 的删除尚未做**，见 §10。
> 下文常量为**已实现值**（与代码一致，改动请同步此表）。

```
第一层（快，零扣留）                          [待实施，见 §10]
  A（填充语）+ C（接头）合并成 1 个计数器、2 种命中。
  命中次数 >= 5，且相邻间隔 <= 20 字符，且子句 <= 18 字符 -> 熔断。

第二层（深，零扣留，<= 1024 字符内判定）      [已实施]
  R1  内部重复：  重复度 = 行数 / 不同行数 >= 4，且行数 >= 32
  R2  跨通道复读：行回声 = |正文行 ∩ 推理行| / |正文行| >= 0.9（正文 >= 8 行）
  R1 或 R2 成立 -> 熔断。
  行标签： trim -> 小写 -> 去行尾标点 -> 合并空白 -> 长度 >= 2  （不掩码数字）
```

**两条第二层规则各自都只是一个除法**：R1 是一次 `Map` 计数，R2 是一次 `Set` 求交。
没有 8-gram、没有 n-gram 窗口、没有双边比率、没有字符层周期、没有 ABCABC 周期检测。

实测（真实语料 1656 个块，脚本 `tests/verification/verify-two-layer.mts`）：

```
R1 触发 5 个块，健康最大重复度 2.658      -> 阈值 4 留 1.5 倍余量，0 误报
R2 触发 8 个块，健康最大前缀行回声 0.714  -> 阈值 0.9 留 0.186 间隔，0 误报
合计触发 11 / 1656 = 0.66%，逐个核对全部是真循环或真复读
R2 最迟在正文第 897 字符判定（预算 1024）
R2 判定点与输入分块大小无关（1 / 64 / 4096 字符分块结果完全一致）

上线后新增的两条实测约束（§4.9 / §4.10）：
R1 行数门槛 8 -> 32：真实语料中「连续完全相同行」最长游程只有 4；
              10 行 churn 在 209 字符处会误触，最小真阳性在 2560 字符。
R2 行数门槛 4 -> 8：最小真阳性有 22 行正文，8 行仍留 2.75 倍余量；
              同时压掉「4 行全同即 1.0」的小样本判定。
```

**关键简化：两层都不需要扣留（holdback）。**
扣留是为了「已经发出的字要收回」，而 R1/R2 都是**在手头已有的内容上**判定，
判定成立那一刻直接熔断即可，不需要回撤任何字符。
所以上一版争了很久的「1024 字符可见延迟 / 60 字符每秒下首字要等 17 秒」**整体消失**。
1024 是**判定时限**，不是**扣留窗口**。

## 2. 现状盘点 [实测]

现在有**三条互相独立**的流式规则，各自一套常量和计数器：

| 规则 | 文件 | 判据 | 已知缺陷 |
|---|---|---|---|
| A 填充语 | `src/filler.ts` | 短行重复 >= 5，容差 20 | 只认词表内的小词 |
| B 循环 | `src/cycle.ts` | 字符层周期，上限 512 | **对短语池循环完全失明**（§4.4） |
| C 接头 | `src/prefix.ts` | 意图前缀重复 >= 5，容差 20 | 与 A 高度重叠 |

### 2.1 三条规则对灾难形态全部失明 [实测]

```
形态                          FillerGuard  PrefixGuard
填充语洪流                       49 字符       48 字符
接头漂移                         46 字符       45 字符
灾难性复制（长行复读）           -1 失明       -1 失明   <-- 重构动机
健康散文                         -1            -1
```

正是这行「灾难性复制全部失明」证明：**只改参数没用，缺的是判据本身**。

### 2.2 常量重复：设计未收敛的硬证据 [实测]

```
COUNT_LIMIT = 5   (filler.ts:27)  ==  PREFIX_COUNT_LIMIT = 5   (prefix.ts:138)
TOLERANCE   = 20  (filler.ts:35)  ==  PREFIX_TOLERANCE   = 20  (prefix.ts:135)
LETME_MAX   = 18  (filler.ts:38)  ==  LETME_MAX          = 18  (prefix.ts:147)
```

三对常量**同名同义、在两个文件里各写一遍** —— 这不是巧合，是「A 和 C 本来就该是同一条规则」的证据。

## 3. 第一层：A + C 合并（零扣留）

### 3.1 合并依据 [实测]

A 和 C 的判据结构**逐字同构**，只有词表不同：

```
A: 一行是填充语词表中的词 -> 计数器 +1；间隔 > 20 或长度 > 18 则重置
C: 一行以意图前缀开头     -> 计数器 +1；间隔 > 20 或长度 > 18 则重置
```

实测两者触发同一批块（相关性极高），保留两份实现只是把同一个想法写了两遍。

### 3.2 合并判据

```
state = { count: 0, lastHitEnd: -1 }

每完成一行 line（含换行符）:
    trimmed = line.trim()
    hit = 是填充语(trimmed) 或 是意图前缀(trimmed)
    若 hit:
        若 len(trimmed) <= ANNOUNCE_MAX 且 (lastHitEnd < 0 或 本次起点 - lastHitEnd <= ANNOUNCE_GAP):
            count += 1
        否则:
            count = 1
        lastHitEnd = 当前流偏移
        若 count >= ANNOUNCE_COUNT: 熔断
```

### 3.3 一个必须保留的细节：`ANNOUNCE_MAX` 是承重的 [档案]

`LETME_MAX = 18` **不能删**。103k 行扫描的实测数据：

```
上限 12 -> 6597 命中   上限 16 -> 13497   上限 18 -> 13565
     14 -> 13008            20 -> 13579 (+14)   24 -> 13582 (+17)   28+ 饱和
```

18 是拐点。**去掉这个上限会多放进 11,471 行健康推理**。
这是从代码本身看不出来的标定信息，必须连同注释一起保留。

---

### 3.4 ⚠️ 合并时必须保留的**通道策略**（实现期发现的真实回归）[实测]

A（filler 词表）和 C（intent 前缀）合并成**一个**计数器是正确的，
但第一版实现顺手把 `brakeReasoning` 这条通道策略也删掉了，**造成真实回归**。

老设计里 filler 命中在 reasoning 通道上被**否决**，源码给了两个理由：

1. **replay signature**：reasoning 块带 replay signature，截断它会让下一个请求
   丢掉 passback 状态（这是 `signature.ts` 存在的理由）。
2. **证据强度**：私有草稿里的 `Writing.` 比用户读到的正文里的同一个词弱得多。

合并后的实测后果：

```
通道块命中        35   （其中 reasoning 32）
  由 filler 完成的  20   ← 老设计明确否决的那一类，含一个 109,217 字的块
全量语料总命中     11 -> 37
```

**最小修法**：`AnnounceVerdict` 本来就带 `kind` 字段，用它即可，不需要第二个计数器：

```ts
if (target === 'text' || brakeReasoning || av.kind === 'intent') { /* brake */ }
```

计数器在 run 不被采纳时**不重置**：这条 run 是真实的，不同的是**处置方式**，
之后任意一个 intent 命中仍会正常熔断同一条 run。

修复后 [实测]：全量语料（1675 块）总命中 **18**
（`echo` 6 / `repeat` 5 / `announce-intent` 7），**filler-on-reasoning 归零**。

## 4. 第二层：两条极简规则（零扣留，<= 1024 字符）

### 4.1 灾难形态其实是**两种不同的病** [实测]

这是本轮最重要的发现，也是上一版方案翻车的原因：

```
模式 1  内部循环     推理自己反复说同样的话
        d531c71b  115071 字符，10190 行，只有 118 个不同行（重复度 87）
        7858b9d6   51211 字符， 2753 行，只有 356 个不同行（重复度 7.9）

模式 2  跨通道复读   正文逐字复述推理
        928ba8fe  推理 116081 / 正文 116079，行回声 = 1.000
        97a12893  推理 119312 / 正文 119310，行回声 = 1.000
        ec54776e  推理 109217 / 正文 109215，行回声 = 1.000
```

实测的**交集与并集**：

```
只有内部循环   3 个
只有跨通道复读 6 个
两者都有       2 个
并集          11 个
```

**两种病必须两条规则。** 我实测过用**一个**统计量统一它们，全部失败：

```
候选单一统计量            结果
合并流 maxCount>=T        模式 2 完全看不见（那些块 maxCount 只有 2~21，与健康块重叠）
合并流 dupFrac>=T         最多 8/11，且模式 1 里 3 个只有 0.07~0.25
合并流滑动窗 freq>=T      最多 5/11，同时产生 8~20 个健康误报
```

### 4.2 合并流为什么不行 [实测]

「不区分正文/推理，只看一条合并流」——实测更差：

```
口径                灾难召回    健康误报
合并流               1/4        38/1450
只看推理             1/4        36/1450
只看正文             1/4         5/1450
```

合并**不提升召回**，误报却涨 7 倍：推理本来就是草稿空间，
高频出现 `Let me ...` 是**正常**的，合并后它的噪声污染了整条流。

但有一个实测事实让「合并」在**结构上**是安全的：

```
推理在前、正文在后（r+t+ 形状）  2522 个消息
推理与正文交错                    0 个消息
```

**[实测] 推理和正文是顺序关系，不是交错关系。**
所以「正文开始流式输出时，推理已经完整」——这正是 R2 成立的前提。

### 4.3 ❌ 上一版判据已被证伪（**不要再实现它**）

上一版提的是：`8-gram echoR >= 0.90` **且** `coverT` **且** `matched = coverT × len(text) >= 512`。

**证伪反例 [实测]**：模型把推理忠实地改写成正文（16 句各不相同，不是循环）：

```
健康形态    echoR = 1.0000   coverT = 0.8735   matched = 1040  -> 触发（误报）
```

**证伪机制**：`matched = coverT × len(text)` **根本不是独立于 echoR 的第二根轴** ——
正文越长越合法，两者同时上升。扫 floor 0→512，健康集最大 echoR 从未低于 0.9904。
**这根轴不存在。**

### 4.4 ❌ 字符层周期（规则 B）对短语池循环失明 [实测]

官方文档记录：330k 字符的短语池循环，周期上限从 64 试到 4096 **全部返回 0**。
在我实测的 115k 洪流上：

```
字符层  只看见 period=53  span=618      （局部、偶然）
行层    看见 10190 行 / 118 个不同行    （完整、必然）
```

**这解释了 loop-guard README 里的悖论**：把周期上限 64→256→512 一直加大也修不好，
因为量错了**层**，不是上限太小。

### 4.5 ✅ R1：内部重复 —— 一个除法

```
行标签 = trim -> 小写 -> 去掉行尾标点 -> 合并连续空白
重复度 = 行数 / 不同行标签数
重复度 >= FREQ_MIN(4)  ->  熔断
```

**这是 loop-guard 的 concentration 判据，也是它唯一值得移植的东西**（见 §11）。

实测分布（真实语料，推理 >= 1500 字符）：

```
重复度       块数
1.0 - 1.1    1354
1.1 - 1.5      86
1.5 - 2         6
2 - 4           4
4 - 8           2      <-- 阈值 4 在这里
8 - 16          0
16 - 无穷       3
```

阈值 4 的地位 [档案]：loop-guard 用 735 个会话标定 ——
真循环 7.16~22.99 次/行，代码引用与规划 1.40~2.48 次/行，**4 落在中间，两侧约 1.6 倍余量**。

**关于延迟，要诚实**：R1 是累积量。在真实灾难块里它分别在
第 1949 / 8988 / 10661 / 22707 / 34979 字符触发——不是检测慢，
而是**循环内容本身就从那里才开始**。真正的反应延迟是：

```
从「重复开始」到「判定成立」= 225 / 278 / 294 / 353 / 389 字符
```

**R1 有一条数学保证**：重复度 = (H+L)/(H+d)，H 为健康行数、L 为循环行数、d 为循环不同行数。
要它 >= 4 即 L >= 3H + 4d。只要循环**不自己停止**，L 无限增长，
**重复度必然最终越过 4**。也就是说：R1 对任何不终止的循环**一定会触发**，只是早晚。
已知局限：超长健康前缀会稀释（需要循环篇幅约为健康篇幅的 3 倍）。本轮语料未观测到漏报。

### 4.6 ✅ R2：跨通道复读 —— 一次求交

```
推理行集合 R = Set(推理的行标签)          // 推理已完成
正文行标签逐个到达，计数 hit = 命中 R 的行数，seen = 正文行数
lineEcho = hit / seen
seen >= ECHO_MIN_LINES(4) 且 lineEcho >= ECHO_MIN(0.9)  ->  熔断
```

**R2 选行级而不是 8-gram，理由是「简单」，不是「更准」——必须说清楚。**

我一开始把两者做了**不对等的比较**（行回声用整块终值，8-gram 用流式前缀最大值），
得出了「行级间隔 0.30 vs 8-gram 0.13」的结论。**那个比较是错的。**

在**同一口径**（都是「对正文所有前缀取最大值」，也就是真正的流式误报风险）下重测：

```
判据                  触发    健康最大前缀值    阈值     真实间隔
行回声 lineEcho       8/186      0.7143        0.90     0.1857   <-- 更宽
8-gram echoR          8/186      0.7667        0.90     0.1333
```

**两者触发集合完全相同（8 个，0 误报）。**

而且阈值扫描发现：

```
阈值 T    触发    最迟判定点    与健康最大值(0.7143)的间隔
0.70      9         897        -0.0143   <-- 开始误报
0.75      8         897         0.0357
0.80      8         897         0.0857
0.90      8         897         0.1857   <-- 选它：判定点不变，间隔翻倍
1.00      8         897         0.2857
```

**正样本全部是 1.000（逐字复制），所以从 0.80 提到 0.90 一个都不漏，间隔直接翻倍。**
不取 1.00 是因为要留出「正文多了一句自己的过渡句（如 “To summarize:”）」的余量：
22 行的正样本掉一行是 21/22 = 0.954，仍在 0.90 之上。

那为什么还选行级？因为**实现复杂度差一个数量级**：

```
行回声：  Set(推理行)  + 一次 Set.has        —— 约 5 行代码，O(n) 内存 O(1) 每次查询
8-gram：  对推理建 n-gram 集合（推理可达 12 万字符 -> 12 万个 8-gram）
          对正文每个前缀重建 n-gram 集合并求交  —— 内存与常数都大得多
```

在**触发集合与误报完全相同**的前提下，按最小化原则取实现更简单的一方。
**这不是碾压，而是「更简单且不更差」**：把阈值提到 0.90 后，行级的余量（0.186）
已经**宽于** 8-gram 的 0.133，同时实现还少一个数量级。
唯一的代价是行级的判据**粒度更粗**，对「改几个字再复述」不敏感 —— 而这恰好是想要的
（见 §4.3：逐字改写式复述不该被误判）。

如果后续灰度发现行级间隔不够（例如出现 0.75 左右的健康前缀），
**升级到 8-gram 是安全的退路** —— 两者触发集合在本语料上完全一致。

**实测延迟**（正文流式，推理已完整）：

```
正文长度    判定点(字符)
  4369          514
  7155          897   <-- 最坏
  7884          613
109215          573
115071          734
116079          366
119310          772
120036          323
最坏 897 < 1024  ->  预算满足
```

**实测分块无关性**（流式正确性的关键）：

```
输入分块      判定点
1 字符        897 / 323 / 734
64 字符       897 / 323 / 734
4096 字符     897 / 323 / 734    -> 完全一致
```

判定点与分块大小无关，说明规则是**流式安全**的，不会因为网络分块大小而抖动。

### 4.7 为什么两层都不需要扣留

上一版为「字符层周期」设计过一套扣留/释放游标，代价是**恒定 1024 字符可见延迟**：

```
可见延迟      74 -> 1024 字符
60 字符/秒下  首字要等约 17 秒
1024 字符以下的回答  全程不可见
```

R1 和 R2 **都是单调判据**：它们只在**已经收到的内容**上判定，成立即刻熔断，
不需要回撤任何已发出的字符。所以：

1. 删掉整套 `takeSafe` / `published` 扣留游标（规则 B 专用）。
2. `cycleText` 默认关闭的纠结**消失**——没有扣留就没有这个权衡。
3. 第一层本来就是零扣留，两层规则统一，心智负担减半。

**1024 是判定时限，不是扣留窗口。** 这是本版最大的简化。

### 4.8 关于正文字符的处置

R2 判定成立时，正文已经流式输出了最多 897 字符。这些字符**不需要收回**：
熔断意味着结束这一轮，已输出的部分留在会话记录里即可（与现有 B 熔断行为一致）。

## 5. 常量表

### 5.1 检测常量 15 -> 8

```
第一层（3 个）
  ANNOUNCE_MAX      = 18      // 原 LETME_MAX，两份合并为一份，承重（§3.3）
  ANNOUNCE_GAP      = 20      // 原 TOLERANCE / PREFIX_TOLERANCE，两份合并
  ANNOUNCE_COUNT    = 5       // 原 COUNT_LIMIT / PREFIX_COUNT_LIMIT，两份合并

  ECHO_MIN          = 0.9     // 行回声阈值，流式口径实测间隔 0.186（§4.6）
  ECHO_MIN_LINES    = 4       // 正文至少 4 行才判，防小样本抖动
```

## 7. 「99.9% 命中率」的定义与测量

### 7.1 先说结论：**当前语料在统计上不可能支撑 99.9%**

零漏报 n 次下，精确单边 95% 置信下界：

```
n=2      -> 22.4%      <-- 真正独立的正样本数
n=3      -> 36.8%
n=8      -> 68.8%
n=100    -> 97.0%
n=2995   -> 99.9%      <-- 要宣称 99.9% 所需的最少样本数
```

**分母无法回避**：那 8 个正样本全部是**被判据本身**找出来的 —— 循环论证。
更严的独立性筛查后只剩 **2 个真正独立的顶层会话**：

```
session-3ef35930   cwd = C:\Users\TRI\Downloads\Noname v1.6.6
session-d531c71b   cwd = M:\Codex\.codex
（b923ce6b 是 origin=subagent depth=1，不是顶层会话）
```

### 7.2 建议的验收定义（两部分，可执行）

**定义 A —— 真实语料定性**

```
对冻结快照跑 verify-two-layer.mts，要求：
  R1 与 R2 触发集合 = 人工标注的真灾难集合，无漏报、无误报
  必须同时报告 95% 置信下界（n=2 时是 22.4%），不得只报 100%
```

**定义 B —— 生成器定量**

```
>= 3000 条参数化合成洪流（模式 1 / 模式 2 / 混合），要求：
  0 漏报
  每条 <= 1024 字符内判定
  健康对照集 0 误报，且对照集必须包含：
    合法长引用（引用自己的代码/表格/计划）
    枚举型长列表（Step 1..N / 日志 / 表格行）
    模型忠实复述自己结论的正文
```

### 7.3 这个指标现在**不能**宣称什么

- 不能说「真实场景命中率 99.9%」——样本量差 3 个数量级。
- 不能说「零误报」是普适结论——它部分是**语料属性**（语料里几乎不含合法长引用形态）。
- 定义 B 的数字是**生成器上的**命中率，必须这样标注。

## 9. 风险与误伤分析

| # | 风险 | 严重度 | 缓解 |
|---|---|---|---|
| R1 | 模型合法地反复引用同一段代码 | 中 | 阈值 4 要求**同一行重复 4 次**；引用两次（改前/改后）实测 1.93，不触发 |
| R2 | 模型合法地把结论改写进正文 | **中高** | 见下 |
| R3 | 推理与正文交错（破坏 R2 前提） | 低 | 实测 0/2522；且 R2 只会**少触发**，不会误触发 |
| R4 | 超长健康前缀稀释 R1 | 低 | 需循环篇幅达健康篇幅 3 倍；但不终止的循环必然越过阈值（§4.5） |
| R5 | 阈值是在同一批语料上调出来的（过拟合） | **中** | 定义 B 用生成器独立验证；阈值取 loop-guard 的 735 会话标定值而非本语料最优值 |

### 9.1 R2 是唯一需要人类拍板的风险

R2 会触发「模型把推理逐字写进正文」——而这**在合法场景里也可能发生**
（例如模型刚做完长分析，决定把结论原文贴给用户）。

流式口径下（对正文所有前缀取最大值），健康集最大行回声是 **0.714**，正样本是 1.000。
取值 0.90 后间隔 **0.186**，与 8-gram（0.133）相比反而更宽（§4.6）。
但必须诚实：**这个干净的间隔可能部分是语料属性** —— 语料里几乎没有「合法长逐字引用」的样本。
所以定义 B 的健康对照集**必须显式包含这个形态**（§7.2），否则等于没测。

### 9.2 误伤验证方法

1. 对冻结语料快照跑 `verify-two-layer.mts`，人工核对每个触发块。
2. 生成器健康对照集（含合法长引用）要求 0 误报。
3. 灰度：先只记录不熔断，观察一周真实触发分布，再打开熔断。

## 11. dsh-loop-guard 复用评估 [实测]

仓库 `https://github.com/MrWeiCodes/dsh-loop-guard`（MIT，v1.0.3），本轮克隆核读。

**人类指示：只取检测逻辑，不作为依赖整体引入。**

| 资产 | 移植 | 理由 |
|---|---|---|
| concentration 判据（行数/不同行数 >= 4） | ✅ | **这就是 R1**，735 会话标定过 |
| `LINE_MIN_CHARS = 2` | ✅ | 「`}` `);` 会合法重复上百次」的护栏 |

| `LoopDetector`（跨调用） | ⚠️ 暂缓 | 管「连续 N 次停滞调用」，是 turn 级语义，与流式检测不同层 |

**结论：真正要移植的只有一条判据 —— 行数/不同行数 >= 4。**
这符合最小化原则：一个干净的除法，附带 735 会话的标定余量。
