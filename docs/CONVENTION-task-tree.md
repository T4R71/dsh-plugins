# 约定：任务树的「三段式」形状（2026-10-01 定）

> 用户拍板：「总任务在最上层，第二层是中枢写的，往里的节点是子代理填的」——以后都按这个模式写。
> 先把**归属**说准，再给可执行的形状。

## 一、谁写什么（一手事实，别记错）

| 层 | 谁**建**节点 | 谁**填内容** |
|---|---|---|
| L1 总任务 | 中枢（`task plan` 的根节点） | 中枢：标题＝目标，detail＝判据 |
| L2 阶段 | **中枢**（按时间顺序） | 中枢：短标题 + 「这一阶段的判据/证据出处」 |
| L3 执行节点 | **中枢**（`task dispatch bind=` 或 `task run` 建） | **子代理回传**：结语末尾的状态行 + 摘要，由插件写进 `status`/`detail`；中枢也可显式 `step` 覆盖 |
| L4 子代理自己的步骤 | **子代理自己**（在它自己的树里 `plan`/`step`） | 子代理自己 |

**关键事实（第 1 阶段实测）**：树**按会话 id 隔离** —— 子代理**无法**在父树里建节点或改状态，
它调 `task step` 只会抛 `task-tree: no node with id "…" in this session's tree`。
所以「L3 由子代理填」在**内容**上成立、在**建节点**上不成立；子代理真正自己写的是 **L4 它自己那棵树**。

## 二、L4 怎么出现在父树里

面板与 `task list scope=tree merge=N` 都会**在读侧合并**：按节点上的 `assignedTo`（＝子会话 id）
把子代理自己那棵树拼到对应节点下（面板深度 2，工具侧 `merge` 由调用方给）。
合并**只在读取侧发生**，一个字节都不写回 —— 子代理对自己被拼进父树一无所知。
⇒ 想看到 L4，派活时要照现有角色预设那样**要求子代理用 `task` 的 plan/step 记在自己那棵树上**。

## 三、固定形状

```
- L1 总任务：<这一轮要达成什么>            detail: 判据 + 证据出处
  - L2 ① 接手/现状核对                     detail: 判据
    - L3 <执行节点>（中枢建，子代理回传状态与摘要）
      - L4 <子代理自己树的步骤>（读侧 merge，自动出现）
  - L2 ② …
```

规矩：
1. **L2 一律按时间顺序编号**（①②③…），一个阶段一件事，标题短。
2. **L3 只挂在它所属的那个 L2 下**，不要平铺在根上（本次重排就是因为平铺才显得乱）。
3. `detail` 只写**判据与证据出处**，不写过程流水；过程留在子代理自己的树里。
4. **阶段封口再开下一个**：不在同一层留"进行中"和"已完成"混着看不出来的情况。

## 四、一个必须记住的坑

`task plan` 带 `replace: true` 时，**不在本次列表里的节点会被丢弃**，而且**留下节点的
`status` 与 `assignedTo` 都会被重置成初始态**（本次实测：重排后所有节点变 `pending`，owner 标记全丢）。
所以：
- 重排**必须**把要保留的节点全部列进去；
- 重排之后**逐个 `step` 把真实状态补回去**；
- 或者干脆只用「只增不删」的写法（`replace` 省略）来调整，别整体重写。
